# Management Intelligence v5
## Domain Model Translation Specification

**Status:** Active implementation specification  
**Branch:** `mi-v5`  
**Phase:** 2.1 Domain Model Translation  
**Scope:** First implementation slice  
**Tenancy Model:** Multi-tenant from initial schema

---

# 1. Purpose

This document translates the frozen Management Intelligence business architecture into an implementation-ready relational and SQLAlchemy model specification.

It governs the first implementation slice and must be used before creating ORM models or Alembic migrations.

The governing rule is:

> Every persisted business record belongs to exactly one Enterprise tenant unless explicitly classified as platform-owned metadata.

Managed Store remains the canonical dealership accountability object. Enterprise is the canonical tenant boundary.

Multi-tenancy is not a later security enhancement. It is part of identity, relationships, uniqueness, querying, authorization, testing, and migration design from the first database revision.

---

# 2. Canonical Tenancy Model

```text
PLATFORM
   │
   ├── ENTERPRISE TENANT A
   │       ├── Organizational Groups
   │       ├── Managed Stores
   │       ├── Departments
   │       ├── Employees, Roles, and Assignments
   │       ├── Financial Periods
   │       ├── Evidence
   │       └── Measurements
   │
   └── ENTERPRISE TENANT B
           └── Fully isolated business records
```

## 2.1 Tenant Boundary

`Enterprise` is the tenant root.

Every tenant-owned table must include a non-null `enterprise_id`, either as its primary key for the Enterprise table or as a foreign key for all descendant records.

## 2.2 Managed Store Boundary

`ManagedStore` is the canonical dealership operating and accountability object inside an Enterprise tenant.

A tenant may contain one Managed Store or many Managed Stores.

A Managed Store is never used as the global tenant boundary because one customer may operate multiple stores and require enterprise-wide intelligence.

## 2.3 Isolation Rules

- No foreign key may connect records across Enterprises.
- All repositories and services require an explicit tenant context.
- All business-key uniqueness constraints are tenant-scoped unless documented otherwise.
- Every query against tenant-owned data must be filtered by `enterprise_id`.
- Cross-tenant reads are prohibited outside explicit platform-administration functions.
- Tenant isolation must be tested at model, repository, service, and API layers.
- Database row-level security may be added, but application-layer tenant scoping remains mandatory.

## 2.4 Platform-Owned Metadata

Platform-owned metadata is allowed only when the information is truly shared across all tenants, such as a governed list of supported country codes or unit definitions.

Platform-owned metadata must be explicitly classified. Absence of `enterprise_id` is never accidental.

# 3. Shared Implementation Standards

## 3.1 Naming

- SQLAlchemy classes use singular PascalCase.
- Tables use singular snake_case.
- Primary keys use `<object>_id`.
- Foreign keys use the referenced primary-key name.
- Timestamps use UTC and end in `_at`.
- Effective dates use `effective_from` and `effective_to`.

## 3.2 Primary Keys

All business objects use UUID primary keys generated by the application or database.

UUID identity supports tenant-safe import, distributed processing, offline creation, and future data migration without exposing sequential record counts.

## 3.3 Required Tenant Field

Every tenant-owned table includes:

```text
enterprise_id UUID NOT NULL
```

Each tenant-owned relationship should use composite referential enforcement where practical so a child cannot reference a parent belonging to another tenant.

## 3.4 Audit Fields

Every mutable tenant-owned object includes:

```text
created_at
created_by_id
updated_at
updated_by_id
version
```

`created_by_id` and `updated_by_id` may be nullable only for governed system ingestion before an authenticated Employee or service principal is available.

## 3.5 Retirement and Deletion

Operational master records use soft retirement rather than destructive deletion.

Historical Evidence, Measurements, Assignments, and closed Financial Period records are retained.

Physical deletion is limited to test data, failed imports before publication, or controlled privacy and legal workflows.

## 3.6 Effective Dating

Objects that represent changing organizational membership or accountability use:

```text
effective_from TIMESTAMPTZ NOT NULL
effective_to TIMESTAMPTZ NULL
```

Open-ended records use `effective_to = NULL`.

Overlapping active periods are prohibited when the relationship is logically exclusive.

## 3.7 Status Values

Status values are stored using stable string-backed enums or governed lookup values. Database representation must remain readable and migration-safe.

## 3.8 Tenant-Aware Uniqueness

Business keys use composite uniqueness with `enterprise_id`.

Example:

```text
UNIQUE (enterprise_id, dealer_code)
```

A business key may repeat in another Enterprise without conflict.

# 5. Enterprise

## Purpose

Tenant root representing one subscribing operating organization.

## SQLAlchemy Class and Table

```text
Enterprise
enterprise
```

## Primary Key

```text
enterprise_id UUID
```

## Required Attributes

- `name`
- `slug`
- `status`
- `default_timezone`
- `country_code`
- `created_at`
- `updated_at`
- `version`

## Optional Attributes

- `legal_name`
- `external_reference`
- `activated_at`
- `retired_at`

## Status

- `provisioning`
- `active`
- `suspended`
- `retired`

## Relationships

- Organizational Groups: one-to-many
- Managed Stores: one-to-many
- Departments: one-to-many through Managed Stores
- Employees: one-to-many
- Roles: one-to-many
- Assignments: one-to-many
- Financial Periods: one-to-many
- Evidence: one-to-many
- Measurements: one-to-many

## Unique Constraints

- `slug` globally unique
- `external_reference` unique when present and governed by platform provisioning

## Indexes

- `status`
- `slug`

## Delete and Retention

Enterprise records are never cascade-deleted with business history.

Retirement preserves all tenant records and disables new operational activity.

# 6. Organizational Group

## Purpose

Optional, recursive grouping inside an Enterprise, including Market, Region, District, Division, Platform, or custom hierarchy.

## SQLAlchemy Class and Table

```text
OrganizationalGroup
organizational_group
```

## Primary and Foreign Keys

- `organizational_group_id UUID`
- `enterprise_id UUID NOT NULL`

## Required Attributes

- `name`
- `group_type`
- `status`
- `effective_from`

## Optional Attributes

- `code`
- `description`
- `effective_to`
- `retired_at`

## Relationships

Recursive parent-child relationships are stored in `organizational_group_hierarchy` and are effective dated.

Managed Store membership is stored in `organizational_group_store` and is effective dated.

## Constraints

- `UNIQUE (enterprise_id, code)` when code is present
- Parent and child must share `enterprise_id`
- Recursive cycles are prohibited
- Duplicate active parent-child relationships are prohibited

## Delete and Retention

Soft retirement only after referenced memberships are closed or transferred.

Historical group relationships remain queryable.

# 11. Assignment

## Purpose

Effective-dated relationship that records who held what Role in which organizational context and when.

## SQLAlchemy Class and Table

```text
Assignment
assignment
```

## Primary and Foreign Keys

- `assignment_id UUID`
- `enterprise_id UUID NOT NULL`
- `employee_id UUID NOT NULL`
- `role_id UUID NOT NULL`
- exactly one governed organizational context reference:
  - `enterprise_context_id`
  - `organizational_group_id`
  - `managed_store_id`
  - `department_id`

## Required Attributes

- `effective_from`
- `status`

## Optional Attributes

- `effective_to`
- `is_primary`
- `source_reference`

## Constraints

- Employee, Role, and context must share `enterprise_id`
- Exactly one organizational context must be populated
- `effective_to` must be later than `effective_from`
- Overlapping exclusive primary assignments are prohibited for the same governed responsibility

## Indexes

- `(enterprise_id, employee_id, effective_from)`
- `(enterprise_id, role_id, effective_from)`
- `(enterprise_id, managed_store_id, effective_from)`
- `(enterprise_id, department_id, effective_from)`

## Delete and Retention

Assignments are immutable after publication except through correction workflow that preserves prior values or audit history.

Assignments are retained permanently because they establish historical accountability.

# 16. Tenant Enforcement Requirements

## ORM

- All tenant-owned models implement a shared tenant mixin.
- Tenant relationships include explicit `enterprise_id` joins.
- Lazy or implicit cross-tenant relationship loading is prohibited.

## Repository

- Repository constructors or methods require a `TenantContext`.
- `get`, `list`, `update`, and `delete` operations always scope by `enterprise_id`.
- Fetching by UUID alone is prohibited for tenant-owned records.

## Service

- Services propagate one immutable tenant context through a transaction.
- Services reject references to records from another Enterprise.

## API

- Enterprise context derives from authenticated authorization, not arbitrary request-body values.
- Client-supplied `enterprise_id` cannot override authorized tenant scope.

## Database

- Tenant fields are non-null.
- Composite uniqueness includes `enterprise_id`.
- Composite foreign keys should enforce same-tenant relationships where supported.
- PostgreSQL row-level security is recommended as defense in depth after the initial schema is stable.

## Tests

At minimum, automated tests must prove:

1. A tenant cannot read another tenant's record.
2. A tenant cannot update or retire another tenant's record.
3. Cross-tenant foreign-key relationships are rejected.
4. Identical business keys may exist in different tenants.
5. Repository methods cannot execute without tenant context.
6. Background jobs retain tenant scope.
7. Evidence and Measurement lineage cannot cross tenant boundaries.

# 18. Definition of Done

Phase 2.1 first-slice translation is complete when:

- Every first-slice business object has a class and table mapping.
- Every tenant-owned table includes `enterprise_id`.
- Managed Store remains the dealership accountability object.
- Enterprise is enforced as the tenant root.
- Business keys are tenant-scoped.
- Same-tenant foreign-key rules are defined.
- Effective-dating rules are explicit.
- Audit and retention behavior are explicit.
- Evidence and Measurement immutability rules are explicit.
- Repository and API tenant-context requirements are explicit.
- Tenant-isolation acceptance tests are defined.
- ORM implementation can proceed without inventing tenancy behavior.
